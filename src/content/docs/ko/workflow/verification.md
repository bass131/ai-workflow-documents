**에이전트는 작업이 준비됐다고 보고하고, 제안한 실행기는 완료 조건을 확인한다.** 테스트는 회귀 위험을 줄이는 근거다. 모든 결함이 없음을 증명하지는 않는다.

## 동작을 바꿀 때의 순서

<div class="document-table document-table--steps" role="region" aria-labelledby="동작을-바꿀-때의-순서" tabindex="0">

| 단계 | 진행을 판단할 근거 |
| --- | --- |
| **RED · 실패 확인** | **기대하는 동작이 없어 실패한다.** 설치 오류나 문법 오류는 그 동작의 실패를 보여주지 않는다. |
| **GREEN · 구현** | **구현이 해당 실패를 해결한다.** 통과하기 위해 검사를 지우거나 기대값을 낮추지 않는다. |
| **정리 · 필요할 때** | **구조를 바꿔도 동작이 유지된다.** 유지보수에 필요한 이유가 있을 때 구조를 고친다. |
| **회귀 확인** | **최종 코드에서 관련 동작도 유지된다.** 수정 전 검사 결과만으로는 부족하다. |

</div>

사용자와 합의한 관찰 가능한 기준에서 AI가 예시와 검사를 만든다. 테스트를 통과하기 쉬운 내부 구현만 검사하면 기준을 만족했는지 알 수 없다.

:::tip[문서만 바뀌는 경우]
주석·설명만 수정했다면 인위적인 RED는 필요 없다. 설명의 사실, 링크, 빌드나 렌더 결과 등 바뀐 내용에 맞는 검사를 한다.
:::

## “완료”와 검증 요청을 나눈다

다음은 **아직 구현하지 않은 실행기 설계**다. 새 작업은 합의한 기준에서 시작하고, 재개할 때는 이전 기록과 남은 예산도 불러온다.

  <figcaption id="completion-map-caption"><strong>시작·재개 → 작업 → 검증</strong><span>제안한 흐름 · 완료를 기록할 권한은 관리 프로그램이 가진다.</span></figcaption>
  <ol class="workflow-map-steps" role="list">

    <li><span class="workflow-map-label">02 · 에이전트</span><strong>구현하고 검증을 요청한다</strong><p>공식 에이전트 실행 기능으로 작업하고, 준비된 결과를 보고한다.</p></li>
    <li><span class="workflow-map-label">03 · 관리 프로그램</span><strong>결과를 검증한다</strong><p>필수 검사를 실행하고 결과를 검사한 코드와 입력에 연결한다.</p></li>
  </ol>
  <ul class="workflow-map-outcomes" role="list">
    <li><strong>검사 통과 + 기준 충족 → 완료</strong><span>해당 작업 결과의 검증 근거를 남긴다.</span></li>
    <li><strong>검사 실패 → 한도 안에서 수정</strong><span>이미 사용한 시도 횟수는 이어받는다.</span></li>
    <li><strong>검사 누락·코드 변경 → 다시 검증</strong><span>이전 결과로 새 작업을 완료 처리하지 않는다.</span></li>
    <li><strong>한도 소진 → 중단하고 기록</strong><span>원인과 남은 작업을 재개 기록으로 남긴다.</span></li>
  </ul>
  <p class="workflow-map-note">합의한 범위 밖의 중요한 결정은 사용자에게 확인한다. 범위 안의 작고 되돌릴 수 있는 선택은 진행할 수 있다.</p>

테스트와 연결할 코드 식별자는 커밋만으로 부족할 수 있다. 커밋되지 않은 파일·설정도 결과에 영향을 주기 때문이다. 실행기는 검사 입력과 실제 작업 트리를 함께 식별해야 한다.

## 검사를 우회하지 못하게 하려면

**스킬로 검사를 안내해도 반드시 실행되는 것은 아니다.** 에이전트가 검사를 건너뛰고 공식 완료 기록까지 바꿀 수 있다면 절차는 선택 사항으로 남는다. CLI 대신 SDK로 연결하는 것만으로 이 문제가 해결되지는 않는다.

제안한 경계는 권한에 있다. 에이전트는 구현을 수정하고 테스트를 제안하지만, 필수 검증 정책·신뢰할 검사 결과·공식 완료 상태는 임의로 바꿀 수 없어야 한다. 관리 프로그램은 통과했다는 보고를 받는 데 그치지 않고 직접 검사를 실행한다. 에이전트에게 수정 권한이 그대로 있다면 폴더나 프로세스만 나눠서는 부족하다.

**가상 예시:** 언어 선택 저장을 고친 뒤 에이전트가 “완료”를 보고했다. 필수인 재방문 검사가 실행되지 않았다면 관리 프로그램은 미완료로 남긴다. 합의한 완료 기준을 바꿀 때는 검토가 필요하며, 통과를 위해 에이전트가 기준을 낮출 수는 없다.

이 구조가 막으려는 것은 **검증 없는 완료 처리**다. 에이전트의 협조나 모든 중간 행동의 절차 준수까지 보장하지는 않는다. 권한 경계와 검사 환경은 앞으로 구현하고 검증해야 한다.

## 실행기가 맡을 책임

**실행기**는 정해진 규칙대로 상태를 바꾸는 프로그램을 뜻한다. AI가 문장을 그럴듯하게 썼는지와 별개로 다음 항목을 통제하도록 제안한다.

- 허용된 상태 전환과 완료 조건
- 검사 명령, 종료 코드, 결과물, 검사한 코드 버전의 연결
- 코드 변경 뒤 오래된 검증의 무효화
- 실패·미실행 필수 검사에 대한 완료 거부
- 재시도와 시간 한도, 재개 후 소비 예산 보존

완료 조건을 프로그램으로 검사해도, 요구사항 자체가 잘못되었거나 테스트가 중요한 동작을 빠뜨린 문제까지 해결되지는 않는다.

## 실패와 한도 소진

실패하면 원인을 분류하고 남은 예산 안에서 수정한다. 한도를 소진하면 시도를 계속 늘리지 않고 실패 근거, 시도한 내용, 남은 작업과 필요한 결정을 남긴다. 새 세션으로 넘어가도 횟수를 초기화하지 않는다.

중요한 권한 밖 결정은 사용자에게 넘긴다. 모든 실패를 즉시 사람에게 보내거나, 반대로 모든 실패를 끝없이 재시도하는 규칙은 두지 않는다.
