이 워크플로의 출발점은 [이 사이트를 만든 이유](../why-this-site/)에 정리했다.

중요한 작업은 **관찰할 수 있는 성공·실패 기준**에서 시작한다. AI가 구현 방법을 선택하되, 완료 여부는 남겨진 증거와 대조한다.

## 01 · 목표를 설정하고 조율한다

<figure class="workflow-illustration">

![사람의 손과 목재 로봇이 같은 도면 위에서 목표 모양, 확인 표식, 작업 경계를 맞추는 장면](../../../../assets/workflow-goal.png)

<figcaption>함께 결과와 작업 경계를 정한다. <span>AI 생성 개념 삽화</span></figcaption>
</figure>

:::tip[목표도 함께 구체화한다]
목표 설정은 **사용자와 AI가 브레인스토밍하며 작업의 방향을 함께 다듬는 과정**이다. 사용자가 처음부터 완성된 요구사항을 준비할 필요는 없다. 의도와 불편을 말하면 AI가 기존 맥락을 살펴 대안과 예시를 제시하고, 사용자는 중요한 결과와 우선순위를 짚는다. 이 대화를 통해 목표·완료 기준·작업 조건을 구체화한다.
:::

아래는 ‘잘못된 설정이 저장되는 문제를 고치는 작업’에 적용한 **가상 예시**다.

<div class="document-table document-table--steps" role="region" aria-labelledby="01--목표를-설정하고-조율한다" tabindex="0">

| 정할 항목 | 확인할 질문과 예시 |
| --- | --- |
| **목표** | **어떤 작업을 할 것인가?**<br>잘못된 설정이 저장되는 문제를 고친다. |
| **완료 기준** | **무엇을 확인하면 끝났다고 볼 수 있는가?**<br>필수 값이 비어 있으면 저장되지 않고, 정상 설정은 저장한 뒤 다시 읽을 수 있다. 기존 설정도 그대로 읽힌다. |
| **작업 조건** | **어디까지 바꾸고, 무엇은 바꾸지 않을 것인가?**<br>설정 검사와 저장 처리는 수정하되, 기존 저장 형식과 화면 전체 구성은 바꾸지 않는다. |

</div>

**중요한 미결정**은 답에 따라 기대 결과·완료 판정·허용 범위가 달라지거나, 되돌리기 어려운 선택이다. 위임 범위 안의 작고 되돌릴 수 있는 구현 선택은 에이전트가 판단한다.

**조율이 반복되면** 같은 질문을 되풀이하지 않고 예시·선택지·작은 시안으로 바꾼다. 횟수를 채웠다는 이유로 중요한 미결정을 임의로 확정하지 않는다. 자세한 여덟 가지 원칙은 [목표와 성공 기준](../goals-and-scope/)에서 설명한다.

## 02 · 단계로 나누어서 관리한다

<figure class="workflow-illustration">

![목재 로봇이 하나의 조립 목표를 여러 작업함의 부품과 메모로 나누는 장면](../../../../assets/workflow-phases.png)

<figcaption>필요한 만큼 나누고 이어갈 맥락을 남긴다. <span>AI 생성 개념 삽화</span></figcaption>
</figure>

**단계별로 진행을 관리하고, 그 안에서 메인이 맥락을 배분하며 구현·검토를 조율한다.** 단계별 문서는 나누어진 작업을 전체 목표에 연결하고, 다음 작업을 이어가는 기준이 된다.

한 목표는 필요한 만큼 **1–7개 단계**로 나눈다. 각 단계는 **달성할 중간 결과와 완료 기준을 갖춘 마일스톤**으로 정의하고, 단계 사이의 순서와 의존성을 드러낸다. 7개는 상한이며 채워야 할 수가 아니다. 작은 작업은 한 단계로 충분하다.

에이전트가 한 번에 다룰 수 있는 맥락에는 한계가 있다. **단계별 문서에 결정과 이유, 검증 근거, 남은 일과 다음 행동을 남기면** 현재 작업에 집중하면서도 이전 단계의 맥락을 다시 찾을 수 있다. 맥락이 압축되거나 세션이 바뀔 때도 이 기록을 기준으로 실제 상태를 확인하고 이어간다.

규모 있는 작업에서는 **메인 오케스트레이터가 목표·조건·의존성과 진행을 관리하고, 구현과 검토를 위임하는 방식**을 기본 방향으로 삼는다. 구현 결과는 검토 에이전트가 실제 변경과 테스트 근거를 확인한 뒤 메인에 전달한다. 메인은 그 결과를 바탕으로 수정 작업을 배정하거나 다음 단계로 진행한다.

<figure class="workflow-map" aria-labelledby="delegation-flow-caption">
  <figcaption id="delegation-flow-caption"><strong>메인은 흐름을 관리하고, 필요한 작업을 위임한다</strong><span>위임할 때의 기본 흐름이다. 모든 작업에 세 에이전트를 요구하는 고정 절차는 아니다.</span></figcaption>
  <ol class="workflow-map-steps" role="list">
    <li><span class="workflow-map-label">메인</span><strong>기준을 유지하고 배정</strong><p>범위·완료 기준과 필요한 맥락을 전달한다.</p></li>
    <li><span class="workflow-map-label">구현</span><strong>맡은 범위를 구현·검사</strong><p>변경 사항·테스트 결과·남은 문제를 남긴다.</p></li>
    <li><span class="workflow-map-label">검토</span><strong>결과와 근거를 확인</strong><p>요구 충족 여부와 수정할 점을 판단한다.</p></li>
  </ol>
  <p class="workflow-map-note"><strong>검토 → 메인:</strong> 판정과 근거를 전달한다. 메인은 수정 배정 또는 다음 단계를 정한다. 중요한 미결정은 사용자와 조율한다.</p>
</figure>

:::tip[필수 정보는 남기고, 수행 방법은 맡긴다]
서브에이전트 수, 직렬·병렬 실행, 도구와 구현 방법은 작업의 규모와 의존성에 맞춰 메인이 선택한다. 작은 작업은 직접 처리할 수 있다. 단계마다 새 세션을 만들거나 특정 모델에 역할을 고정할 필요는 없다. 어떤 배치에서도 **작업 기준, 재개할 맥락, 검증 근거**는 남긴다.
:::

<div class="document-table document-table--steps" role="region" aria-labelledby="02--단계로-나누어서-관리한다" tabindex="0">

| 남길 정보 | 기록할 내용과 쓰임 |
| --- | --- |
| **작업 기준** | **목표·완료 기준·허용 범위.** 맡은 작업이 전체 목표와 어떻게 연결되는지 함께 전달한다. |
| **재개 맥락** | **결정과 이유·현재 상태·남은 일·다음 행동.** 관련 문서와 결과물 위치를 연결해 다른 세션에서도 이어갈 수 있게 한다. |
| **검증 근거** | **실제 변경·검사 결과·검사 대상.** 실패하거나 실행하지 않은 검사도 남긴다. 검토자의 판단만으로 테스트를 대신하지 않는다. |

</div>

메인에는 **진행 판단에 필요한 요약과 근거 위치**를 전달하고, 상세 내용은 필요할 때 확인한다. 요약 때문에 중요한 조건이나 미해결 문제가 사라지지 않게 한다. 단계 문서는 대화 전체를 복사하는 대신 이후 작업의 기준점을 제공한다.

단계와 에이전트는 일대일로 대응하지 않는다. 기록 예시와 상태 확인 방법은 [단계 기록과 재개](../phase-and-resume/)에서 다룬다.

## 03 · 동작을 바꾸고 확인한다

<figure class="workflow-illustration">

![목재 로봇이 맞지 않는 부품과 맞는 부품을 비교하며 검사 틀 안에서 조정하는 장면](../../../../assets/workflow-testing.png)

<figcaption>기대한 동작을 확인하며 수정한다. <span>AI 생성 개념 삽화</span></figcaption>
</figure>

**합의한 동작을 테스트로 표현하고, 그 테스트가 실패하는 이유를 확인한 뒤 구현한다.** 테스트 작성과 구현은 에이전트가 맡고, 기대 결과나 허용 범위를 바꾸어야 한다면 사용자와 다시 조율한다.

다음은 01의 ‘잘못된 설정 저장을 막는 작업’을 이어가는 **가상 예시**다.

<div class="document-table document-table--steps" role="region" aria-labelledby="03--동작을-바꾸고-확인한다" tabindex="0">

| 단계 | 예시와 확인할 근거 |
| --- | --- |
| **RED · 실패 확인** | **빈 필수 값의 저장을 거부하는 테스트를 만든다.** 기존 코드가 잘못된 값을 저장해서 실패하는지 확인한다. 설치 오류나 문법 오류는 이 동작의 실패 근거가 아니다. |
| **GREEN · 구현** | **저장 전에 값을 검사해 테스트를 통과시킨다.** 정상 설정의 저장·재조회와 기존 설정 읽기도 확인한다. 통과를 위해 기대값을 낮추거나 검사를 지우지 않는다. |
| **정리 · 회귀 확인** | **필요한 구조 정리 후에도 동작이 유지되는지 확인한다.** 중복이나 책임이 뒤섞인 부분을 필요할 때 정리하고, 최종 코드에서 관련 검사를 다시 실행한다. |

</div>

테스트는 내부 함수의 모양보다 **사용자가 기대하는 결과**를 확인해야 한다. 통과는 검사한 조건에서의 근거이며, 모든 결함이 없다는 보장은 아니다. 실패하면 원인과 근거를 남기고 해당 작업을 수정한다.

문서·주석만 바꾸는 작업에는 인위적인 실패 테스트를 만들지 않는다. 대신 사실·링크·빌드 결과와 실제 화면의 가독성을 확인한다. 자세한 검사 기준은 [TDD와 완료 검증](../verification/)에서 다룬다.

## 04 · 근거로 완료를 판단한다

<figure class="workflow-illustration">

![목재 로봇 옆의 측정 장치가 완성 부품을 검사하고 확인 기록이 함께 놓인 장면](../../../../assets/workflow-evidence.png)

<figcaption>완료 판단은 실제 결과와 검사 근거에 연결한다. <span>AI 생성 개념 삽화</span></figcaption>
</figure>

**AI의 “완료” 보고를 검증 요청으로 받아들이고, 실제 결과와 완료 기준을 대조한다.** 각 마일스톤의 결과뿐 아니라 전체 목표가 충족됐는지도 확인한다. 나누어 구현한 기능이 함께 동작해야 한다면 그 연결도 검사 대상에 포함한다.

<figure class="workflow-map" aria-labelledby="overview-completion-caption">
  <figcaption id="overview-completion-caption"><strong>작업 결과 → 필수 검사 → 완료 판단</strong><span>제안 중인 실행기의 흐름 · 아직 구현되지 않은 설계다.</span></figcaption>
  <ol class="workflow-map-steps" role="list">
    <li><span class="workflow-map-label">에이전트</span><strong>검증을 요청한다</strong><p>변경 사항, 확인한 결과와 남은 문제를 전달한다.</p></li>
    <li><span class="workflow-map-label">실행기</span><strong>직접 검사를 실행한다</strong><p>결과를 검사한 코드·설정·입력과 연결한다.</p></li>
    <li><span class="workflow-map-label">완료 판단</span><strong>기준과 근거를 대조한다</strong><p>필수 검사 통과와 합의한 결과 충족을 확인한다.</p></li>
  </ol>
  <ul class="workflow-map-outcomes" role="list">
    <li><strong>기준 충족 + 유효한 근거 → 완료</strong><span>완료 상태와 검사 근거를 함께 기록한다.</span></li>
    <li><strong>실패·누락·검사 후 변경 → 미완료</strong><span>남은 한도 안에서 수정하거나 다시 검사한다.</span></li>
  </ul>
</figure>

설정 저장 예시에서 빈 값 거부만 통과하고 정상 설정의 재조회 검사를 빠뜨렸다면 완료 근거가 부족하다. 검증 뒤 저장 코드를 바꾼 경우에도 **이전 검사 결과를 새 코드의 근거로 쓰지 않는다.** 실패하거나 실행하지 않은 필수 검사를 구분해 남긴다.

**상태 통제의 세부 설계는 [TDD와 완료 검증](../verification/)에서 다룬다.** 상태 전환, 완료 기록의 권한, 코드 변경 뒤 재검증, 재시도·시간 한도와 재개 규칙을 그 문서에서 확인한다. 실행기가 RED → GREEN 순서까지 강제할지는 미정이다.

## 애매하면 어떻게 하나

<figure class="workflow-illustration">

![사람의 손과 목재 로봇이 서로 다른 모양의 부품과 선택지를 함께 살펴보는 장면](../../../../assets/workflow-ambiguity.png)

<figcaption>결과를 바꾸는 중요한 선택을 함께 조율한다. <span>AI 생성 개념 삽화</span></figcaption>
</figure>

**모호함이 생기면 먼저 확인 가능한 사실과 사용자가 결정할 선택을 나눈다.** 코드나 문서에서 확인할 수 있는 내용을 사용자에게 다시 설명하게 하지 않는다. 답에 따라 기대 결과·완료 기준·허용 범위가 달라지는지가 판단 기준이다.

아래도 설정 저장 작업에 적용한 **가상 예시**다.

<div class="document-table document-table--steps" role="region" aria-labelledby="애매하면-어떻게-하나" tabindex="0">

| 상황 | 진행 방법 |
| --- | --- |
| **확인 가능한 사실** | **기존 저장 형식을 모른다.** 관련 코드·문서·테스트를 먼저 확인한다. |
| **위임 범위 안의 선택** | **검사 로직을 어느 함수로 분리할지 정한다.** 작고 되돌릴 수 있는 구현 선택은 에이전트가 판단하고, 이어서 작업할 때 필요한 이유를 남긴다. |
| **결과·권한을 바꾸는 선택** | **잘못된 값을 거부하는 대신 자동 보정하고 싶다.** 기대 결과가 바뀌므로 추천안과 영향을 설명하고 사용자와 조율한다. 기존 데이터를 삭제하는 등 되돌리기 어려운 조치도 먼저 확인한다. |

</div>

답을 기다릴 때는 **그 답에 의존하는 작업만 멈추고**, 이미 허용된 독립 작업은 이어간다. 되돌릴 수 있다는 이유만으로 요청 밖의 일을 추가하지 않는다. 중요한 미결정이 풀리면 질문을 끝내며, 대화가 반복될 때는 [예시·선택지로 조율하는 원칙](../goals-and-scope/)을 적용한다.

## 모델이 좋아지면 절차도 다시 본다

<figure class="workflow-illustration">

![목재 로봇이 같은 결과물을 만드는 복잡한 고정 장치와 단순한 장치를 비교하는 장면](../../../../assets/workflow-revisit.png)

<figcaption>같은 기준으로 비교하고 필요한 절차를 판단한다. <span>AI 생성 개념 삽화</span></figcaption>
</figure>

**절차는 해결하려던 문제에 실제로 도움이 되는지 확인하며 유지한다.** 단계나 에이전트 수가 늘었다고 품질이 좋아졌다고 볼 수 없고, 모델이 바뀌었다고 기존 검증을 바로 없앨 근거도 되지 않는다.

비교할 때는 같은 시작 상태·작업·모델·완료 기준에서 절차 하나를 바꿔 본다. 모델 자체를 비교한다면 절차는 유지해 차이의 원인을 구분한다. 한 번의 성공만으로 모든 작업에 같은 효과가 있다고 결론 내리지 않는다.

- **결과:** 요구사항 누락이나 회귀가 있었는지, 최종 결과가 기준을 충족했는지 본다.
- **판단 부담:** 사용자가 같은 맥락을 다시 설명하거나 중요하지 않은 선택을 반복 확인해야 했는지 본다.
- **작업 비용:** 소요 시간, 재시도, 확인 가능한 사용량과 비용을 기록한다. 측정하지 않은 값은 추정치와 구분한다.

예를 들어 모든 단계에서 새 세션을 시작하는 방식과 필요할 때만 교체하는 방식을 비교할 수 있다. 이는 **비교 실험의 예시이며, 어느 쪽이 더 낫다는 측정 결과는 아니다.** 도움이 확인된 절차는 유지하고, 부담만 늘어난 절차는 줄이거나 다시 설계한다. 선택의 이유와 재검토 조건은 [현재 선택과 재검토 기준](../../design/decisions/)에 연결한다.

## 앞으로 채워 갈 장

<figure class="workflow-illustration">

![목재 로봇이 안내 지도를 펼치고 주제별 책자가 놓인 문서함을 살펴보는 장면](../../../../assets/workflow-reading.png)

<figcaption>전체 흐름에서 필요한 주제의 설명으로 들어간다. <span>AI 생성 개념 삽화</span></figcaption>
</figure>

**필요한 질문에 맞춰 상세 문서를 선택한다.** 전체 흐름은 각 단계의 관계를 설명하고, 구체적인 기준과 기록 형식은 아래 문서에서 다룬다.

1. **무엇을 만들고 어디까지 할 것인가?** [목표와 성공 기준](../goals-and-scope/)에서 브레인스토밍과 질문을 마치는 기준을 확인한다.
2. **무엇을 맡기고 언제 확인할 것인가?** [자율성과 확인이 필요한 결정](../autonomy/)은 위임 경계의 개요다. 세부 사례는 더 구체화할 예정이다.
3. **다른 세션이 어떻게 이어받을 것인가?** [단계 기록과 재개](../phase-and-resume/)에서 마일스톤별 결정·근거·다음 행동을 남기는 방법을 확인한다.
4. **어떤 근거로 완료를 판단할 것인가?** [TDD와 완료 검증](../verification/)에서 검사 기준과 제안한 실행기의 책임·한계를 확인한다.

실제 관찰은 [AgentDeck에서 배운 것](../../experiments/agentdeck/)에서 확인한다. 사례의 관찰 결과와 앞으로 구현할 워크플로 설계를 구분해 읽는다.

:::note[설계와 구현의 경계]
이 사이트는 워크플로를 설명하는 프로토타입이다. 상태를 통제하는 실제 실행기는 아직 구현하지 않았다.
:::
