이 위키는 AI와 개발할 때 **목표·에이전트의 자율성·검증·재개**를 어떻게 구성할지 설명한다. 개념과 적용 방법을 사례, 설계 선택의 근거와 연결해 찾아볼 수 있게 한다.

에이전트에게는 일할 자율성을 주고, 꼭 지켜야 할 조건은 프로그램이 확인하는 방향이다. 사이트는 구현되어 있지만 워크플로 관리기는 제안 단계이며, 효과는 실제 작업에서 검증해야 한다.

![목재 로봇이 흩어진 메모와 부품을 문서함과 재사용할 조각으로 정리하는 작업대](../../../../assets/workflow-workbench.png)

*흩어진 정보와 코드를 정리해 다시 활용한다는 뜻을 담은 AI 생성 개념 삽화다. 실제 작업 화면이나 측정 결과는 아니다.*

**프로그램의 역할은 정해 둔 조건의 준수를 확인하는 것**이다. 요구사항이나 테스트가 충분한지, 중요한 결과를 받아들일지는 여전히 사람의 판단이 필요하다.

## 어떤 문제가 있었나

아래는 이 위키의 배경이 된 프로젝트에서 보고된 문제와 그에 따른 설계 제안이다. 개선 제안의 효과는 실제 작업에서 확인해야 한다.

<div class="document-table document-table--comparison" role="region" aria-labelledby="어떤-문제가-있었나" tabindex="0">

| 프로젝트에서 보고된 문제 | 개선 제안 |
| --- | --- |
| **책임이 뭉친 코드**<br>여러 책임이 한곳에 있고 기존 코드를 충분히 재사용하지 않았다. | **수정 지점과 재사용할 코드가 보이게**<br>기존 함수를 찾기 쉽게 만들고, 다음 변경을 고려한다. |
| **현재와 과거가 섞인 문서**<br>현재 규칙, 예전 계획, 반복된 설명이 섞였다. | **주제와 시점을 구분하기**<br>주제마다 내용을 둘 곳을 정하고, 과거 기록과 현재 기준을 구분한다. |
| **반복해서 재구성하는 맥락**<br>사용자가 필요한 정보를 고르고 맥락을 다시 설명해야 했다. | **다음 작업자가 이어받을 근거 남기기**<br>결정 이유, 현재 상태, 검증 근거를 남긴다. |

</div>

기능이 동작해도 다음 수정이 어려울 수 있었다. 작업을 이어받은 에이전트가 오래된 설명을 따르거나 끝난 일을 다시 할 여지도 있었다. 코드의 재사용성과 유지보수성, 문서의 정리가 함께 필요한 이유다.

## 작은 작업에 대입해 보면

**가상 예시: 선택한 언어가 재방문할 때 유지되지 않는 문제를 고친다.** 이 사이트의 언어 기능을 소재로 한 설명이며, 아래 과정이 실행기로 자동화됐다는 뜻은 아니다.

<div class="document-table document-table--steps" role="region" aria-labelledby="작은-작업에-대입해-보면" tabindex="0">

| 단계 | 이 작업에서는 |
| --- | --- |
| **01 · 기준 합의** | **선택한 언어를 유지한다.** 같은 브라우저로 대표 홈에 다시 왔을 때 적용한다. 직접 연 문서 주소의 언어는 존중한다. |
| **02 · AI의 작업** | **기존 코드를 재사용하고 테스트와 수정을 작성한다.** 언어·주소·저장 코드를 찾아 기대 동작을 확인한다. |
| **03 · 프로그램의 확인** | **최종 코드의 필수 검사 결과를 확인한다.** 실패하거나 실행하지 않은 필수 검사가 있으면 완료로 넘기지 않는다. |

</div>

<details>
<summary>검사 뒤 코드가 바뀌거나 작업이 끊기면?</summary>

- **검사 뒤 수정했다면:** 이전 통과 결과를 새 코드의 완료 근거로 쓰지 않는다. 필요한 검사를 다시 실행한다.
- **다른 에이전트가 이어받는다면:** 목표, 결정 이유, 남은 일과 실제 코드 상태를 대조한다. 사용한 재시도 횟수도 이어받는다.
- **완료했다고 보고했다면:** 그 말을 검증 요청으로 취급한다. 제안한 실행기가 기록된 조건을 확인한 뒤 완료 여부를 결정한다.

상태 보관과 한도 적용은 [제안 중인 완료 검증](../verification/)의 역할이다. 이 사이트에 이미 구현된 기능은 아니다.

</details>

## 이 위키를 읽는 방법

1. **가이드에서 적용 방법을 찾는다.** 목표, 권한, 맥락 보존, 완료 검증을 주제별로 설명한다. 공통 개념은 한곳에 두고 관련 문서에서 링크한다.
2. **사례에서 근거를 확인한다.** 조건, 관찰, 한계를 읽은 뒤 다른 프로젝트에도 적용할 수 있는지 판단한다. 제안과 측정 결과를 구분한다.
3. **설계 결정에서 트레이드오프를 읽는다.** 선택 이유와 재검토 조건을 보고 작업에 맞는지 판단한다. 변경 이력은 Git으로 보존하며 본문은 세션별 작업 일지로 구성하지 않는다.

<details>
<summary>예전 워크플로의 규칙은 그대로 가져오나?</summary>

일부 규칙은 당시 모델과 도구를 전제로 만들었다. 도구가 달라지면 규칙도 다시 검토해야 한다. 절차나 단계, 에이전트 수가 많다는 이유만으로 결과가 좋아졌다고 볼 수는 없다.

제안한 워크플로는 목표·성공 기준·범위를 함께 정하고, 일하는 방법은 메인 에이전트가 선택하며, 결과의 동작을 검증하는 구조다. 위임 밖의 중요한 결정은 의논하고, 작고 되돌릴 수 있는 선택마다 승인을 반복하지 않는다.

</details>

## 개선 여부를 판단하는 기준

읽기 쉬운 코드, 재사용, 주제별 문서, 테스트를 출발점으로 삼는다. 작은 변경과 [AgentDeck 사례](../../experiments/agentdeck/)를 평가할 때는 다음 항목을 확인한다.

- 에이전트가 수정할 곳과 재사용할 코드를 찾기 쉬워졌나?
- 오래된 설명이나 중복 구현 때문에 같은 일을 반복하지 않았나?
- 사람이 맥락을 다시 설명하고 결과를 검토하는 부담이 줄었나?

AI 준비도 점수만으로 개선됐다고 판단하지 않는다. 세부 워크플로와 검증 방법은 아직 확정되지 않았다.

이어서 [전체 흐름](../overview/) 또는 [현재 설계 선택](../../design/decisions/)을 읽을 수 있다.
