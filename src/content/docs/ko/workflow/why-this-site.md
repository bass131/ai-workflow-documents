---

프로젝트가 커질수록 AI가 작성한 코드와 문서를 관리하는 일이 어려워졌다. **필요한 맥락을 찾고, 변경 이유를 이해하고, 결과를 믿을 수 있는지 판단하는 부담**이 커진 것이 출발점이다.

이 사이트에는 그 부담을 줄이기 위해 시도하는 방법과 확인한 결과를 남긴다. 에이전트에게는 일할 자율성을 주고, 꼭 지켜야 할 조건은 프로그램이 확인하도록 설계하고 있다.

![목재 로봇이 흩어진 메모와 부품을 문서함과 재사용할 조각으로 정리하는 작업대](../../../../assets/workflow-workbench.png)

*흩어진 정보와 코드를 정리해 다시 활용한다는 뜻을 담은 AI 생성 개념 삽화다. 실제 작업 화면이나 측정 결과는 아니다.*

**프로그램의 역할은 정해 둔 조건의 준수를 확인하는 것**이다. 요구사항이나 테스트가 충분한지, 중요한 결과를 받아들일지는 여전히 사람의 판단이 필요하다.

## 어떤 문제가 있었나

내 프로젝트에서 겪은 문제와 개선하고 싶은 방향을 나란히 정리했다. 아래 방향이 실제로 도움이 되는지는 앞으로 작업을 통해 확인해야 한다.

| 겪은 문제 | 개선하고 싶은 방향 |
| --- | --- |
| 여러 책임이 한곳에 뭉쳐 있고 기존 코드를 충분히 재사용하지 않았다. | 수정할 위치와 기존 함수를 찾기 쉽게 만들고, 다음 변경을 고려한다. |
| 현재 규칙, 예전 계획, 반복된 설명이 문서에 섞였다. | 주제마다 내용을 둘 곳을 정하고, 과거 기록과 현재 기준을 구분한다. |
| 필요한 정보를 고르고 맥락을 다시 설명하는 일이 내 몫으로 남았다. | 결정 이유, 현재 상태, 검증 근거를 이어받을 수 있게 남긴다. |

기능이 동작해도 다음 수정이 어려울 수 있었다. 작업을 이어받은 에이전트가 오래된 설명을 따르거나 끝난 일을 다시 할 여지도 있었다. 코드의 재사용성과 유지보수성, 문서의 정리가 함께 필요한 이유다.

## 작은 작업에 대입해 보면

**가상 예시: 선택한 언어가 재방문할 때 유지되지 않는 문제를 고친다.** 이 사이트의 언어 기능을 소재로 한 설명이며, 아래 과정이 실행기로 자동화됐다는 뜻은 아니다.

| 단계 | 이 작업에서는 |
| --- | --- |
| 기준 합의 | 같은 브라우저로 대표 홈에 다시 왔을 때 선택한 언어를 유지한다. 직접 연 문서 주소의 언어는 존중한다. |
| AI의 작업 | 기존 언어·주소·저장 코드를 찾아 재사용하고, 기대 동작을 확인하는 테스트와 수정을 작성한다. |
| 프로그램의 확인 | 최종 코드에 필요한 검사가 실행됐는지 확인한다. 실패하거나 실행하지 않은 필수 검사가 있으면 완료로 넘기지 않는다. |

<details>
<summary>검사 뒤 코드가 바뀌거나 작업이 끊기면?</summary>

- **검사 뒤 수정했다면:** 이전 통과 결과를 새 코드의 완료 근거로 쓰지 않는다. 필요한 검사를 다시 실행한다.
- **다른 에이전트가 이어받는다면:** 목표, 결정 이유, 남은 일과 실제 코드 상태를 대조한다. 사용한 재시도 횟수도 이어받는다.
- **완료했다고 보고했다면:** 그 말을 검증 요청으로 취급한다. 제안한 실행기가 기록된 조건을 확인한 뒤 완료 여부를 결정한다.

상태 보관과 한도 적용은 [제안 중인 완료 검증](../verification/)의 역할이다. 이 사이트에 이미 구현된 기능은 아니다.

</details>

## 왜 사이트로 남기는가

1. **필요한 설명을 찾기 위해.** 작업 시작, 중요한 결정, 재개, 검증을 주제별로 나눈다. 공통 설명은 한곳에서 고치고 링크로 연결한다.
2. **판단 근거를 남기기 위해.** 실제 사례, 선택 이유, 검증 범위와 한계를 기록한다. 제안과 확인한 결과를 구분한다.
3. **변화를 보여주기 위해.** 문서를 작업에 맞춰 갱신하고 Git으로 이력을 보존한다. 포트폴리오에서도 문제와 접근 과정을 보여준다.

<details>
<summary>예전 워크플로의 규칙은 그대로 가져오나?</summary>

일부 규칙은 당시 모델과 도구를 전제로 만들었다. 도구가 달라지면 규칙도 다시 검토해야 한다. 절차나 단계, 에이전트 수가 많다는 이유만으로 결과가 좋아졌다고 볼 수는 없다.

지금 합의한 방향은 목표·성공 기준·범위를 함께 정하고, 일하는 방법은 메인 에이전트가 선택하며, 결과의 동작을 검증하는 것이다. 위임 밖의 중요한 결정은 의논하고, 작고 되돌릴 수 있는 선택마다 승인을 반복하지 않는다.

</details>

## 앞으로 무엇으로 판단할까

읽기 쉬운 코드, 재사용, 주제별 문서, 테스트를 출발점으로 삼는다. 실제 개선 여부는 작은 변경과 [AgentDeck 사례](../../experiments/agentdeck/)에서 다음 질문으로 확인하려 한다.

- 에이전트가 수정할 곳과 재사용할 코드를 찾기 쉬워졌나?
- 오래된 설명이나 중복 구현 때문에 같은 일을 반복하지 않았나?
- 사람이 맥락을 다시 설명하고 결과를 검토하는 부담이 줄었나?

AI 준비도 점수만으로 개선됐다고 판단하지는 않을 것이다. 세부 워크플로와 검증 방법은 계속 다듬는 중이다.

이어서 [전체 흐름](../overview/) 또는 [현재 설계 선택](../../design/decisions/)을 읽을 수 있다.
