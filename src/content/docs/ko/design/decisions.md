이 문서는 현재 설계의 이유를 모은다. **문서 사이트는 구현되어 있고, 작업의 상태·검증·한도를 통제할 실행기는 제안 단계다.** 아래 선택은 더 나은 근거가 생기면 바꾼다.

*설계 상태 기준일: 2026년 9월 18일.*

## 목표와 근거를 중심에 둔다

**선택:** 중요한 작업의 성공·실패 기준을 먼저 합의하고, 완료 판단에 검사 결과와 대상 코드를 연결한다.

**이유:** AI의 설명과 실제 결과는 다를 수 있다. [AgentDeck](../../projects/agentdeck/)은 여기서 사례로 다루는 데스크톱 AI 개발 도구다. 이 프로젝트의 [검사 스크립트 실험](../../experiments/agentdeck/)에서도 세션 종료 확인과 목표 달성 확인의 범위를 구별할 필요가 있었다.

**재검토:** 검사를 통과해도 요구 동작을 놓치는 사례가 생기면 기준과 테스트를 보완한다. 검사 수만 늘리지 않는다.

## 절차와 분업은 작업에 맞춘다

**선택:** 한 목표를 필요한 만큼 1–7개 단계로 나눈다. 메인 세션이 에이전트 수와 직렬·병렬 실행을 고른다.

**이유:** 고정 팀이나 단계별 세션 초기화가 모든 작업에서 이롭다는 비교 근거는 없다. 중요한 이유와 제약, [재개 기록](../../workflow/phase-and-resume/)을 유지하는 것이 우선이다.

**재검토:** 같은 시작 상태·모델·완료 기준에서 절차 하나를 바꿔 정확성과 총비용을 비교한다. 아직 이 비교를 수행하지 않았다.

## 공식 에이전트 실행 기능을 재사용한다

**선택:** AgentDeck의 기존 Claude Agent SDK 연결을 유지하고, Codex를 추가할 때 App Server로 연결한다. 그 위에서 AgentDeck이 맡을 책임으로 **목표·검증·재개**를 제안한다. 공통 워크플로 관리기와 Codex 연결은 아직 구현되지 않았다.

**이유:** 공식 도구의 발전을 따라가면서 실행 기능까지 다시 만들면 유지보수 부담이 커진다. 기존 기능을 활용하면 작업 기준, 검증, 재개 기능에 개발 범위를 집중할 수 있다.

**트레이드오프:** 직접 유지할 실행 코드가 줄지만, 사용할 수 있는 제어와 이벤트는 제공자의 지원 범위에 따라 달라진다. 공통 인터페이스는 작게 두고, 모델 배정이나 워크플로 정책은 별도로 설계한다. SDK나 App Server를 연결했다고 그 정책까지 생기지는 않는다. 연결 방식은 [Claude Agent SDK 개요](https://code.claude.com/docs/en/agent-sdk/overview)와 [Codex App Server 문서](https://learn.chatgpt.com/docs/app-server)를 참고한다.

**재검토:** 실제 작업에서 필요한 제어나 이벤트가 없을 때, 빠진 기능을 먼저 확인한 뒤 연결부 확장이나 대체 구현을 판단한다.

## 완료 통제는 실행기의 책임으로 제안한다

**선택:** 상태 전환, 필수 검사, 코드 변경 뒤 검증 무효화, 재시도·시간 한도를 정해진 규칙으로 처리한다. 필수 정책·신뢰할 검사 결과·공식 완료 기록은 작업 에이전트의 수정 권한 밖에 둔다.

**이유:** 한 분기의 빠른 반환 때문에 한도 검사를 지나친 사례가 있었다. AI의 “완료”를 검증 요청으로 취급하고 모든 경로에서 조건을 확인해야 한다.

**한계:** 스킬은 사용법을 안내하지만 실행 자체를 보장하지 않는다. CLI·SDK·App Server 중 무엇으로 연결했는지만으로 우회를 막을 수는 없다. [검증 설계](../../workflow/verification/)에서 필요한 권한 경계를 설명한다.

**남은 일:** 작은 작업에서 권한 경계를 구현하고 실패 분기, 오래된 결과, 재개 시나리오를 검증한다. 통제하려는 것은 완료 조건이며 모든 중간 행동은 아니다.

## 문서는 코드와 함께 관리한다

**선택:** Astro의 맞춤 홈과 Starlight의 Markdown 문서를 함께 사용한다. 배포 대상으로 GitHub Pages를 선택했다.

**이유:** 변경 내용을 Git에서 비교하고, 검증을 통과한 정적 결과를 게시할 수 있다. 서버·계정·데이터베이스 없이 현재 문서 범위를 운영하기에 맞는다.

**제약:** 검색은 production build로 만든 색인이 필요하다. GitHub Pages의 저장소 하위 경로에서 링크·자산·검색이 함께 동작해야 한다. 배포 설정과 운영 상태는 저장소의 배포 가이드에 기록한다.

## 이어서 논의할 항목

완료에 필수 검사 통과를 요구한다는 원칙은 유지한다. 실행기가 RED → GREEN 순서까지 강제할지는 미정이다. 검증 누락을 얼마나 줄이는지와 단계별 강제에 드는 부담을 확인한 뒤 판단해야 한다.

## 변경 기록을 남기는 기준

새로운 실험이나 설계 수정이 생기면 해당 문서에서 **바뀐 선택, 이유, 근거, 남은 한계**를 갱신한다. 이전 관찰은 당시 조건과 날짜를 보존하고, 현재 상태로 오해할 표현을 고친다. 단순 문장 수정까지 별도 결정 기록으로 늘리지는 않는다.
