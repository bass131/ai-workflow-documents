# 문서 작성

## 먼저 위치를 고른다

- `workflow/why-this-site.md`: 사이트를 만든 이유와 확인하려는 방향
- `workflow/overview.md`: 전체 흐름과 공통 원칙
- `workflow/goals-and-scope.md`: 목표·성공 기준·포함/제외 범위
- `workflow/autonomy.md`: 요청 안의 자율성과 확인할 결정
- `workflow/phase-and-resume.md`: 단계 기록과 재개
- `workflow/verification.md`: TDD와 제안한 완료 통제
- `experiments/agentdeck.md`: 문제 → 관찰 → 설계 선택 → 한계
- `projects/agentdeck.md`: AgentDeck의 용도, 주요 기능, 워크플로·위키와의 관계
- `design/decisions.md`: 현재 선택의 이유와 재검토 기준

같은 설명을 여러 페이지에 복사하기보다 원래 문서를 고치고 링크합니다. 새로운 내용이 독립된 독자 질문을 해결할 때 페이지를 추가합니다. 운영 방법은 이 `docs/`에, 방문자가 읽을 내용은 `src/content/docs/`에 둡니다. 메뉴의 기준은 `src/data/navigation.ts`이며 홈과 Starlight 설정이 함께 사용합니다.

## 위키 문체와 문서 역할

사이트는 독자가 개념과 방법을 찾아 쓰는 위키입니다. 글쓴이의 하루나 대화 순서를 따라가야 이해되는 구성은 피합니다.

프로젝트나 도구를 처음 언급할 때는 무엇인지 한 문장으로 설명하고 소개 문서로 연결합니다. 독자가 이름만으로 프로그램의 용도나 위키와의 관계를 안다고 가정하지 않습니다.

- **개념·가이드:** 무엇인지, 어떤 문제에 쓰는지, 역할과 적용 조건을 먼저 설명합니다. 필요한 경우 절차·예시·한계를 덧붙이며 모든 문서에 같은 틀을 강제하지 않습니다.
- **사례:** 대상·조건·관찰·근거·한계를 구분합니다. 개인 프로젝트에서 나온 관찰을 일반적인 사실로 넓히지 않고, 실제 관찰 날짜와 수치를 보존합니다.
- **설계 결정:** 현재 선택, 이유, 트레이드오프와 재검토 조건을 설명합니다. 구현·제안·보류 상태를 표시하되 합의 대화나 작업 중계를 본문에 옮기지 않습니다.
- **일지·인수인계:** 세션별 진행 상황, 다음 작업자에게 할 말, 로컬 브랜치 목록은 운영 기록에 둡니다. 위키에는 독자의 이해나 적용에 필요한 상태만 남깁니다.

예를 들어 ‘오늘 SDK를 유지하기로 했다’보다 ‘공식 실행 기능을 재사용하면 직접 유지할 코드가 줄지만, 제어 범위는 제공자의 지원에 따라 달라진다’처럼 선택과 영향을 설명합니다. ‘앞으로 알아보자’로 끝내기보다 아직 검증하지 않은 항목과 판단 기준을 밝힙니다. 문체를 바꿔도 원래 의도·조건·불확실성을 바꾸지 않습니다.

## Markdown / MDX

일반 문서는 Markdown을 기본으로 합니다. 컴포넌트가 실제로 필요하면 Starlight가 지원하는 MDX를 사용합니다.

```md
---
title: 독자가 찾는 주제를 구체적으로
description: 이 문서에서 이해하거나 결정할 수 있는 내용을 한 문장으로.
---

현재 상태와 핵심 내용을 짧게 적습니다.

## 이유
선택의 이유와 제약을 설명합니다.
```

Starlight가 title로 H1을 만들므로 본문에 H1을 반복하지 않습니다. H2/H3가 오른쪽 목차가 됩니다. 새 경로는 소문자와 하이픈으로 짧게 만들고, `src/data/navigation.ts`의 알맞은 그룹에 slug를 추가합니다. 기존 경로를 바꿀 때는 링크·검색·기존 공유 주소의 영향을 확인합니다.

## 읽기 쉬운 구성

사람과 AI가 모두 읽기 좋은 문서를 목표로 합니다. 사람은 시각 자료로 개념·관계·방법을 빠르게 파악하고, AI도 제목·본문·표에서 같은 의미와 조건을 읽을 수 있어야 합니다. 긴 설명을 형식만 바꿔 늘리거나 모든 문서에 같은 장식을 넣지 않습니다.

- 첫 문단에서 이 글의 질문과 핵심 내용을 짧게 밝힙니다. 제목·소제목만 읽어도 흐름을 짐작할 수 있게 나눕니다.
- 개념의 구성 요소, 방법의 단계, 순서·분기·역할 관계는 개념도·흐름도·도해로 풀어봅니다. 비교와 대응 관계는 Markdown 표로 보여주고, 실제 동작은 주석을 붙인 화면이나 예시로 설명합니다. 이미지 생성도 개념을 시각화하는 데 활용하며, 정확한 절차·수치는 수정 가능한 도표를 우선합니다. 간단한 나열은 목록으로 충분합니다.
- 추상적인 설명에는 구체적인 예시를 붙입니다. 가상 예시, 실제 관찰, 제안, 구현된 기능을 가까운 곳에 표시합니다.
- 배경이나 예외처럼 따로 읽을 만한 세부 설명은 Markdown 안의 details/summary로 접을 수 있게 만듭니다. 핵심 결론·중요한 조건·한계는 접힌 내용에만 숨기지 않습니다.
- 사진·스크린샷·삽화는 내용을 이해하는 데 도움이 될 때 사용합니다. image_gen으로 만든 개념 삽화는 AI 생성임을 밝히고 실제 화면이나 근거처럼 표현하지 않습니다. 정확한 절차와 수치는 그림 속 글자에만 넣지 않습니다.
- 원문의 의도, 적용 조건, 확실성 수준을 보존합니다. 읽기 좋게 줄이는 과정에서 사실을 단정하거나 사용자 생각을 새로 만들어 넣지 않습니다.

핵심 정보는 이미지 안에만 두지 않습니다. 의미 있는 제목, 본문, 표, 대체 텍스트로 내용을 남기고 그림과 글의 용어·조건을 맞춥니다. 같은 규칙을 여러 페이지에 복제하지 말고 기준 문서로 연결합니다. 시각 자료가 바뀌면 관련 텍스트도 함께 확인합니다. AI 작업 성능의 개선 여부는 실제 작업에서 따로 확인합니다.

이미지는 대체 텍스트와 짧은 설명을 붙이고 출처를 기록합니다. 다이어그램의 글자는 확대·검색·복사가 가능하게 두며, 좁은 화면에서는 읽는 순서대로 배치합니다. 양쪽 언어와 밝음·어두움 테마에서 글자 대비, 표의 스크롤, 키보드로 세부 내용 펼치기를 확인합니다. 적용 예시는 [이 사이트를 만든 이유](../src/content/docs/ko/workflow/why-this-site.md)에 있습니다.

### 강조와 비교

강조는 독자가 단계, 핵심, 설명을 구분하는 데 사용합니다. 굵은 글씨나 색이 들어갔다는 사실 자체가 완료 기준은 아닙니다.

- **단계·역할:** 표의 첫 열에 짧은 이름을 굵게 둡니다. 실제 순서가 있을 때만 번호를 붙이고, 구체적인 작업 설명은 다음 열에 둡니다.
- **핵심과 설명:** 한 셀이나 문단에서 판단에 필요한 짧은 구절을 강조합니다. 설명이 길면 핵심을 먼저 한 줄로 보여주고 뒤에 풀이를 둡니다. 문장 전체를 연달아 굵게 만들지 않습니다.
- **비교 관계:** 같은 행에서 같은 대상을 비교합니다. ‘기존 / 변경 후’, ‘겪은 문제 / 개선 제안’처럼 열 제목만 읽어도 관계와 상태가 드러나게 씁니다. 아직 확인하지 않은 방향을 ‘개선된 결과’로 표시하지 않습니다.
- **색의 역할:** 비교하는 열의 제목과 핵심 구절에 절제된 색을 보조적으로 사용합니다. 색만으로 이전·이후, 성공·실패를 전달하지 않고 글자·위치로도 구별합니다. 중요한 조건과 예외의 대비를 낮추지 않습니다.

사이트에서 강조가 필요한 Markdown 표는 `document-table` 래퍼 안에 둡니다. 두 열 비교에는 `document-table--comparison`, 단계와 설명에는 `document-table--steps`를 더합니다. 스타일은 `src/styles/theme.css` 한곳에서 관리합니다. 래퍼는 해당 제목을 `aria-labelledby`로 연결하고 `role="region"`, `tabindex="0"`을 지정해 좁은 화면에서도 키보드로 가로 스크롤할 수 있게 합니다. 일반 표까지 모두 이 형식으로 바꿀 필요는 없습니다.

### 화면에서 다시 읽기

문서를 작성하거나 고친 뒤에는 **작성 → Computer Use로 실제 화면 읽기 → 필요한 부분 수정 → 다시 확인**을 거칩니다. 소스와 빌드 결과만 보고 가독성 검토를 끝내지 않습니다.

1. 제목, 단계 이름, 강조 구절만 훑고 무엇이 핵심이며 무엇을 비교하는지 파악되는지 확인합니다. 이어서 전체를 읽어 설명·예외·조건이 빠지거나 다른 뜻으로 보이지 않는지 확인합니다.
2. 기존과 변경 후, 경험한 문제와 제안한 방향, 개념의 핵심과 보충 설명이 화면에서도 구별되는지 봅니다. 모두 강조돼 차이가 사라지거나 색만 보고 판단해야 한다면 문구·배치·강조 범위를 고칩니다.
3. 수정한 페이지의 영어·한국어, 밝음·어두움 테마, 좁은 화면을 확인합니다. 표가 잘리거나 글자가 과도하게 줄바꿈되는지, 가로 스크롤을 키보드로 사용할 수 있는지도 봅니다.

보고할 때는 확인한 페이지와 화면 조건, 발견해 고친 점, 남은 문제를 짧게 남깁니다. 이 검토는 작성자의 화면 점검이며, 실제 독자가 더 잘 이해했다는 측정 결과로 표현하지 않습니다. 화면 확인이 불가능하면 그 한계를 명시합니다.

## 링크와 이미지

빌드 경로에는 저장소 이름이 붙을 수 있습니다. 문서의 내부 링크는 출력 URL 기준 상대 경로를 씁니다.

- 같은 workflow 폴더: `[검증](../verification/)`
- workflow에서 사례: `[AgentDeck](../../experiments/agentdeck/)`
- 사례에서 공개 근거: `[측정](../../evidence/agentdeck-stop-gate-excerpt.json)`

원시 `/workflow/...` 링크는 Pages base를 벗어나므로 쓰지 않습니다. Astro 템플릿에서는 `import.meta.env.BASE_URL`을 붙입니다. 외부 자료는 실제 출처 페이지에 연결합니다.

이미지는 설명에 필요할 때만 추가하고 대체 텍스트를 씁니다. 문서 이미지의 권장 위치는 `src/assets/`이며 Markdown 파일에서 상대 경로로 참조합니다. 직접 제공해야 하는 다운로드는 `public/`에 두되 그대로 공개된다는 점을 확인합니다. 출처·사용 권한·개인 정보가 불명확한 이미지는 먼저 확인합니다.

## 문장과 상태

각 언어로 구체적인 문제, 선택, 이유, 근거, 한계를 적습니다. 코드에서 바로 읽히는 동작을 다시 설명하지 말고 외부 제약과 판단 이유를 남깁니다. 추상 용어는 필요한 곳에서 풀어 쓰고, 길이를 줄이려고 중요한 조건을 지우지 않습니다.

구현됨·측정됨·제안은 문장 가까이에서 구별합니다. 실행기 설계를 설명한다고 실행기가 구현된 것은 아닙니다. 가상 예시와 시뮬레이션은 명시하고, 임의 수치나 과장된 성과를 넣지 않습니다.

## 근거와 수정 이력

측정값에는 관찰 날짜, 입력/대상, 측정 범위, 한계를 붙입니다. 이미지를 포함한 원본 전체를 옮기기 전에 공개에 필요한 최소 발췌를 고릅니다. 현재 AgentDeck JSON은 두 종료 훅 조건만 담고 있으며 비공개 원본 보고서나 전체 실행 로그를 포함하지 않습니다.

과거 관찰의 조건과 날짜를 보존합니다. 새 실험 없이 수치나 결론을 갱신하지 않습니다. 중요한 설계 변경은 관련 문서에 바뀐 선택·이유·근거·남은 일을 기록하고, 단순 문장 수정은 Git diff로 충분합니다.

## 확인과 게시

문서 변경은 `npm run verify`와 해당 페이지·링크·목차 확인이 기본입니다. 인위적인 RED는 만들지 않습니다. UI·링크 방식·배포 설정을 바꾸면 [배포 가이드](deployment.md)의 하위 경로와 브라우저 검증도 수행합니다. 게시·실패 확인·되돌리기는 같은 가이드를 따릅니다.

## 시각 스타일

밝은 테마는 참나무·종이 색, 어두운 테마는 중성 차콜 읽기 면과 작은 목재 색 강조를 사용합니다. 어두운 본문 전체에 갈색을 입히지 않습니다. 공유 색상은 src/styles/theme.css의 --wf-*와 Starlight --sl-* 토큰이 기준입니다. 홈의 레이아웃은 src/styles/home.css에 있습니다. 목재 배경은 src/assets/wood049-color.jpg를 사용하며 Astro가 768px WebP로 최적화합니다. 상단바 전체 면과 홈의 흐름도·왼쪽 탐색·오른쪽 목차 프레임에 반복하고, 본문은 정적인 종이 질감을 사용하고, 문서 목록·목차·조작 면은 읽기 대비를 확보합니다. 프레임은 CSS 배경이므로 장식 이미지이며 별도의 대체 텍스트가 필요하지 않습니다. [이미지 출처와 사용 조건](asset-credits.md)을 보존합니다. 문서 목록과 본문 목차는 Starlight 기본 컴포넌트를 유지합니다. 전체 문서 목록은 홈·문서의 공통 버튼과 DocumentDrawer로 열고 닫습니다. WorkshopPageFrame은 문서 화면의 패널 배치와 본문 공간 회수를 맡습니다. 색상을 바꾸면 밝음·어두움·자동 모드, 검색·사이드바·코드·상황 버튼, 모바일과 키보드 초점을 함께 확인합니다. 테마 선택은 starlight-theme 키로 문서와 홈이 공유합니다.

상단바는 WorkshopBrand와 SectionNav를 홈·문서가 공유합니다. 문서의 검색과 테마는 기본 Starlight 컴포넌트를 사용하며 모바일 테마 선택은 상단 아이콘에 남깁니다. 문서 헤더 높이는 --sl-nav-height로 고정 헤더·목차·앵커 간격과 함께 바꿉니다. 좁은 화면에서는 제목을 의도된 두 줄로 배치하고, 데스크톱 섹션 링크는 왼쪽 탐색이 대신합니다.

상단바는 전체 폭·높이에 실제 목재 이미지를 반복합니다. 밝은 모드에는 밝은 참나무 덮개, 어두운 모드에는 채도를 낮춘 짙은 덮개를 사용하며 나뭇결을 남깁니다. 검색·테마·문서 목록 버튼은 작은 단색 조작 면을 사용하고 브랜드·메뉴는 목재 위에 잉크색으로 놓습니다. 본문의 승인된 정적 종이 질감과 읽기 대비를 유지합니다. 헤더의 대비는 CSS 단색 계산만으로 판단하지 말고 실제 텍스처와 덮개의 합성색도 확인합니다.

문서 목록은 첫 방문에 닫히며 사용자의 열림·닫힘 선택을 같은 origin에 저장합니다. 페이지 이동·새로고침·뒤로/앞으로에서도 유지하고, 본문 클릭이나 문서 선택으로 자동 닫지 않습니다. 버튼·닫기·Escape로 변경합니다. 넓은 화면에서는 본문 공간을 나누고, 좁은 화면에서는 헤더 아래 높이가 제한된 비모달 목록으로 배치해 본문을 가리지 않습니다. 저장소를 사용할 수 없으면 현재 페이지의 토글은 동작하되 방문 간 기억은 보장하지 않습니다. Escape·초점 복원·터치·reduced-motion을 함께 검사합니다. 목재 로봇은 홈의 작은 장식이며 최초 한 번 등장하고 정지합니다. 이미지 크기와 투명도는 양쪽 테마에서 확인합니다.

본문 바탕은 로컬 SVG 입자와 낮은 농도의 색상 덮개를 겹친 정적인 종이 질감입니다. 라이트는 따뜻한 종이색, 다크는 중성 짙은 회색을 유지합니다. 배경이 글자·링크·코드 대비를 해치지 않도록 조절하며 움직이는 노이즈는 사용하지 않습니다. 목재 헤더와 패널 프레임은 별도 재질을 유지합니다.

## 언어와 번역

영어는 src/content/docs/의 기본 문서이며, 한국어는 ko/ 아래에서 같은 slug를 사용합니다. 기존 /workflow/... 등 공유 주소는 영어의 같은 문서로 유지됩니다. 한국어 문서는 /ko/workflow/...에서 읽습니다. src/data/languages.ts가 지원 언어·경로·표시 이름의 유일한 목록입니다. Starlight locales, 언어 선택, 수동선택 저장값 검증이 이 목록을 사용합니다.

- 공유 UI는 src/content/i18n/en.json과 ko.json, Astro.locals.t로 번역합니다. 추가 키는 src/content.config.ts의 스키마에 등록합니다. 검색·테마·목차 등 기본 UI는 Starlight 번역을 사용합니다.
- 홈과 네 상황은 src/data/home-en.json과 home-ko.json에 있습니다. src/data/home.ts의 타입이 두 언어의 필수 항목을 검사합니다. 홈 구조는 src/components/WorkshopHome.astro 하나를 공유합니다.
- 문서 간 상대 링크는 언어 안에 머뭅니다. 공통 공개 자산 evidence/로 연결할 때는 영어 문서의 ../../evidence/와 한국어 문서의 ../../../evidence/처럼 깊이를 맞춥니다. locale가 있는 Astro 링크는 languageHref를, 공통 자산은 BASE_URL을 사용합니다.
- 언어 전환은 같은 slug의 문서로 이동합니다. 누락된 문서는 Starlight의 기본 영어 본문과 미번역 안내를 표시하며 본문 lang도 영어로 표시합니다. 영어·한국어 문서 9개씩을 관리하며 모두 번역되어 있습니다.

첫 방문은 영어입니다. 사용자가 언어 선택기를 직접 바꿀 때만 wf-language를 localStorage에 기록합니다. 대표 홈으로 재방문하면 저장 언어 홈으로 이동하고, 명시적인 문서 또는 /ko/ 주소는 해당 경로의 언어를 우선합니다. 문서 링크를 여는 것만으로 저장 선호를 덮어쓰지 않습니다. 내부 탐색은 현재 경로의 언어를 따릅니다. 브라우저 언어 자동감지나 계정 동기화는 하지 않습니다. 손상·미지원 저장값과 저장소 차단은 대표 홈에서 영어로 돌아갑니다. 차단 상태에서도 직접 언어 URL과 현재 언어 전환은 사용할 수 있습니다. 테마와 문서 목록은 기존 별도 저장키를 유지합니다.

언어를 추가하려면 레지스트리에 코드·경로·이름을 추가하고, 동일 slug 문서·UI JSON·home-코드.json을 번역한 다음 home.ts에 사전을 등록합니다. 수동선택/저장검증/언어경로/404는 목록을 따라 확장됩니다. sidebar label의 translations에도 새 코드의 이름을 넣고, check-i18n-browser.mjs의 언어별 검색어를 추가합니다. 검색 색인은 각 언어의 홈과 9문서가 있어야 통과합니다. 번역을 점진적으로 시작할 때는 미번역 안내를 확인하고 공개 범위를 별도로 검토합니다.

GitHub Pages는 단일 404.html을 제공하므로 /ko/ 아래 없는 주소는 /ko/404/ 안내로 연결합니다. 이 페이지는 noindex이며 문서 목록·언어 선택·해당 언어 홈 링크를 제공합니다. 언어별 canonical/alternate, 검색 분리, 320–1440px 조작 영역, 테마·목록 선호 유지, 저장 실패와 URL 우선순위는 npm run test:pages에서 검사합니다.

참고: [Starlight 국제화](https://starlight.astro.build/guides/i18n/)의 root locale, 동일 slug, UI 사전, 기본 언어 fallback을 사용합니다.
